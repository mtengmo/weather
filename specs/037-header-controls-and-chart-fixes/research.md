# Research: Header Controls Cleanup and Chart Bug Fixes

## US1/US2 — Header restructuring

**Decision**: Replace `DisplayMenu` (a dropdown containing `ThemePicker` + `UnitToggle` + `HighLowToggle`) with two independent header controls: a new `ThemeToggle` (always-visible single button, no dropdown, cycling only "midnight"/"ivory") and a new `SettingsMenu` (same dropdown-panel pattern `DisplayMenu` already used, now holding only `UnitToggle` + `HighLowToggle`).

**Rationale**: `ThemePicker.tsx` currently renders 3 buttons (Midnight/Bright/Glass) inside the dropdown. The request wants theme collapsed to one always-visible toggle with only 2 states, entirely outside any menu — that's a different interaction shape than "3 buttons in a panel," so `ThemePicker` is replaced rather than reused. `UnitToggle`/`HighLowToggle` are unchanged internally; only their container changes.

**Alternatives considered**: Keeping `DisplayMenu` and just editing `ThemePicker`'s button count — rejected because the request explicitly asks for the theme control to move *out* of any menu ("one button switch on header"), not just fewer options inside the existing menu.

## US2 — Removing "Glass" and changing defaults

**Decision**: `Theme` narrows from `"midnight" | "ivory" | "glass"` to `"midnight" | "ivory"`. `theme.ts`'s `VALID_THEMES` drops `"glass"`; a stored `"glass"` value now fails that validity check and `getThemePreference()` naturally falls back to `DEFAULT_THEME` ("midnight" → displayed as "Dark"), satisfying FR-005b with no special-case code. `DEFAULT_HIGH_LOW_VISIBLE` flips `true → false`. `DEFAULT_NEARBY_STATION_COUNT` flips `4 → 0`.

**Rationale**: The existing `getThemePreference()` already has an unknown-value fallback path (`if (stored && VALID_THEMES.includes(stored)) return stored; ... return DEFAULT_THEME`) — removing `"glass"` from `VALID_THEMES` reuses that existing mechanism instead of adding new logic, and automatically satisfies "falls back to Dark" since `DEFAULT_THEME` is already `"midnight"`.

**Alternatives considered**: An explicit `if (stored === "glass") return DEFAULT_THEME` special case — rejected as redundant with the existing generic fallback.

## US3 — Temperature degree-scale bug

**Finding**: `WeatherIconOverview.tsx`'s `buildTicks()`/`dedupeCloseTicks()` were already reverted to their non-zero-forcing form in a prior session (`036-declutter-temperature-scale`, commit `d9a5fff`), which fixed exactly this failure mode (a forced 0° tick colliding with and displacing a real boundary tick's label). Re-deriving the reported screenshot's numbers (visible values 11-20°C) against the *current* code: `buildTicks` yields `[10, 20]` (two ticks, `dedupeCloseTicks` no-ops on ≤2 ticks) — i.e. "10°" and "20°", not the reported "0°" and "20°". The reported symptom exactly matches the *old, already-fixed* bug's signature for this same input range (forcing start toward 0 would yield `[0, 10, 20]`, and the old dedupe logic could then drop the middle "10" under a clamp collision, leaving visible "0°"/"20°" — precisely what the screenshot shows).

**Decision**: Treat this as likely still-stale client state (this app is a PWA via `vite-plugin-pwa` with `registerType: "autoUpdate"`, but no `registerSW`/controller-change reload is wired up in `main.tsx` — an already-open tab or an installed PWA can keep running a previously-cached bundle indefinitely after a deploy, with no prompt to refresh). Verify current behavior is already correct via updated/expanded tests (multi-day-view fixtures matching the screenshot's exact values), and additionally slightly widen the tick-label safe margin (`TICK_LABEL_SAFE_MIN/MAX_PERCENT`, currently 8/92) to give a bit more breathing room from adjacent rows, addressing the "touches the row above/below" visual complaint defensively even though the label container already has `overflow: hidden` and SVG gridlines are clipped by the UA default `overflow: hidden` on the root `<svg>`.

**Alternatives considered**: A larger rewrite of the tick algorithm — rejected; the numbers already check out against the current code, so the highest-value fix here is verification (via tests reproducing the exact screenshot data) plus a small safety margin, not a rewrite. Wiring up a service-worker update-prompt/auto-reload — a real, separate improvement, but out of scope for this spec (not requested); noted for a future feature if staleness is confirmed live.

## US4 — 3-day/7-day zoom dead-space bug

**Finding**: `.weather-timeline` uses `width: max-content; min-width: 900px` by default, overridden to `width: 100%` by a conditional `.weather-timeline-fill` class whenever `displayMode !== "last-24-hours"` (so 3-day *and* 7-day both already attempt to stretch-to-fill, contrary to the initial assumption that only 7-day did). Combined with `grid-template-columns: repeat(N, 1fr)`, this fluid layout is more exposed to browser-zoom subpixel-rounding drift (a well-known class of bug: at non-100% zoom, fractional pixel track sizes can round down across many columns, accumulating a visible gap) — and a 3-day view's fewer, wider columns make any such rounding shortfall much more visible per-column than 7-day's narrower columns or 24h's fixed-width (`max-content`, no fill override) columns.

**Decision**: Replace the conditional `width: 100%` override with a single, permanent rule on the base `.weather-timeline` class: `min-width: 100%` *in addition to* the existing `width: max-content` (rather than replacing it). `width: max-content` still lets the box grow to its true natural content width when that's wider than the container (preserving the horizontal-scroll fallback on narrow viewports, exactly like 24h today); `min-width: 100%` gives it a floor so it still fills a wide viewport when narrower than 100%, without a second competing `width` declaration whose class-based toggling was the likely source of the drift. This removes the `weather-timeline-fill` class and its conditional entirely — 24h, 3-day, and 7-day all get identical sizing behavior, directly matching the user's own observation that "24h works a lot better."

**Alternatives considered**: Keeping the class-based toggle but auditing for a specific rounding fix — rejected in favor of unifying all three views under one simpler rule, since the user explicitly points to 24h's (simpler, non-toggled) behavior as the standard to match. This is a CSS-only, layout-affecting change that cannot be meaningfully asserted by jsdom (no real box-layout engine); verification is manual (quickstart.md), consistent with how prior CSS-only layout fixes in this codebase have been handled.

## US6 — Temperature-banded line coloring

**Decision**: Represent the band table as a single shared module, `src/services/temperatureColorScale.ts`, exporting the ordered `{ maxC: number | null, color: string }[]` table (11 bands, `maxC: null` for the open-ended hottest band) and a pure function `buildGradientStops(min: number, max: number): { offset: number; color: string }[]` that, for a series' actual min/max temperature, returns the discrete-edge gradient stops (two stops per internal band boundary at the same offset, one in each color, to render a hard edge rather than a blend) needed to color a single SVG/Recharts stroke by a `objectBoundingBox` vertical `<linearGradient>` (`x1=0 x2=0 y1=0 y2=1`) — offset `0%` = the line's own topmost rendered point (its maximum value), `100%` = its bottommost (its minimum value), which is exactly the geometry SVG already gives a `<path>`'s bounding box, so this needs no access to Recharts' internal scale or the axis's (possibly padded/"niced") domain.

**Rationale**: Recharts' `<Line>` renders one flat `stroke` per series; there is no built-in per-segment/per-value coloring. A `gradientUnits="objectBoundingBox"` gradient keyed to the rendered path's own bounding box turns "color by value" into "color by vertical position," which is exactly equivalent for a line chart (Y position *is* the value) — and it's a technique this codebase already uses for the timeline's temperature-row area fill gradient (`<linearGradient id="weather-timeline-temperature-gradient">` in `WeatherIconOverview.tsx`), so it fits an established pattern rather than introducing a new rendering approach. Being pure/stateless, `buildGradientStops` is unit-testable without rendering either chart.

**Alternatives considered**: Splitting the line into one `<Line>`/`<polyline>` per band (nulling out-of-band points, mirroring the existing observed/forecast-split pattern) — rejected as a much larger structural change across ~10 duplicated render blocks in `ObservationChart.tsx`, and it wouldn't handle a single segment that crosses a band boundary mid-segment as cleanly as a gradient does. A smooth (non-hard-edge) gradient — rejected per the spec's own default choice of discrete band segments (Assumptions), though the same `buildGradientStops` function could trivially support a smooth variant later by emitting one stop per boundary instead of two.

**Scope note**: Applied to the primary/selected location's own temperature line only (`WeatherIconOverview`'s temperature row and `ObservationChart`'s `stroke={seriesColor(0)}` occurrences) — nearby-station comparison lines and the high/low reference lines keep their existing fixed colors. The spec's wording ("the temperature line," singular) centers on the viewed location's own reading; re-coloring comparison lines wasn't requested and would clutter a chart that already uses color to distinguish stations.
