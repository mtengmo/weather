# Phase 0 Research: Nearby-Station Name Fix and Temperature/Wind Chart Styling

## 1. Fallback label for a nameless nearby station (FR-001, FR-002)

**Decision**: In `services/smhiProvider.ts`'s `nearestActiveStations`, change `displayName: s.name` to `displayName: s.name?.trim() ? s.name : "Unnamed station"`. This is the single place `StationInfo.displayName` is constructed (both `getObservations`'s own nearest-station lookups and `getNearestStations`, used for every `NearbyStationSeries.station.displayName` shown in the app), so fixing it here fixes every consumer (`ObservationChart.tsx`'s legend/tooltip name strings, `ObservationDetails.tsx`'s column headers) with one change.

**Rationale**: SMHI's own station-list data occasionally has a blank/whitespace `name` field for some stations (confirmed as a real, not hypothetical, data-quality issue during manual testing). A single centralized fallback is simpler and less error-prone than adding a fallback at each of the ~6 call sites that currently interpolate `n.station.displayName` directly into a template string.

**Alternatives considered**: Falling back at each render call site (`` `${n.station.displayName || "Unnamed station"} (...)` ``) — rejected as repetitive and easy to miss on a future new call site; fixing the data at its source (`StationInfo` construction) guarantees every consumer is correct by construction.

## 2. Color convention for temperature/wind high and low (FR-003, FR-004, User Story 2)

**Decision**: Add two new fixed color constants to `components/seriesColors.ts` — `HIGH_COLOR = "#dc2626"` (red) and `LOW_COLOR = "#0ea5e9"` (a sky-blue distinct from both the existing primary-series blue `SERIES_COLORS[0]` (`#2563eb`, used for temperature's "average" line) and from the existing `SERIES_COLORS` palette generally) — applied only to the **primary location's** high/low lines on the temperature and wind 7-day/30-day charts. The "average" line keeps its current `seriesColor(0)` styling, unchanged. Nearby comparison stations keep their existing `seriesColor(i + 1)`/`seriesDash(i + 1)` styling, unchanged (FR-004).

**Rationale**: Matches existing codebase convention — `SERIES_COLORS` is already a fixed, theme-independent hex palette proven legible against all three themes (Midnight, Bright, Glass) in `002-vibrant-award-theme`'s manual verification — introducing two more fixed constants in the same file is the smallest, most consistent change, rather than inventing a new theme-varying CSS-variable mechanism for just two colors. Choosing a `LOW_COLOR` distinct from the existing average line's blue avoids two visually-similar blue lines competing for attention on the same chart (mitigated further by the average line staying solid while high/low keep their existing dashed `"4 2"` pattern, so the three primary lines remain distinguishable by dash pattern alone even before color is considered).

**Alternatives considered**: Theme-varying `--high-color`/`--low-color` CSS custom properties (matching `002-vibrant-award-theme`'s `--accent`/`--accent-2` pattern) — rejected as unnecessary complexity for two colors that don't need to adapt per theme (the existing `SERIES_COLORS` already don't, and read fine across all three); reusing an existing `SERIES_COLORS` entry for high/low — rejected because `SERIES_COLORS[1]` (red) and a nearby station at index 1 already use that exact red, which would make the primary's "high" line indistinguishable from the first comparison station's line when both are shown (accepted as an unavoidable minor edge case with the *new* `HIGH_COLOR`/`LOW_COLOR` too, since they're independent of `SERIES_COLORS`' indexing, but choosing colors outside the existing 6-color rotation minimizes the chance of collision).

## 3. High/low visibility toggle (FR-005, FR-006, FR-007, FR-008, User Story 3)

**Decision**: Add a new persisted boolean preference, `highLowVisible` (default `true`), following the exact shape of the existing `nearbyStationCount`/`unit`/`theme` preferences: a small service (`services/highLowVisibility.ts`) with `get`/`set` functions backed by a dedicated `localStorage` key, plus a `useHighLowVisibilityPreference()` hook, plus a simple on/off UI control (a single checkbox or toggle button, following `UnitToggle.tsx`'s two-button shape) placed in the header controls alongside the theme/unit/nearby-station-count controls.

Unlike `nearbyStationCount` (which changes what's *fetched*, research.md §5 of `003-extended-history-metrics`), this preference only changes what's *rendered* — toggling it does not re-fetch anything, mirroring how `theme`/`unit` are pure display-layer preferences over already-fetched data (SC-003's "within 1 second" target is trivially met the same way SC-008's theme-switch target was in `002-vibrant-award-theme`).

**Rationale**: Same reasoning as `003-extended-history-metrics` research.md §5's nearby-station-count preference — reusing an already-established pattern (localStorage + hook + small control) rather than inventing a new one.

**Scope (FR-008)**: The preference only affects the temperature and wind charts' 7-day/30-day rendering (where `<Line dataKey="primaryHigh">`/`primaryLow` — and the new wind equivalents — are conditionally omitted when `highLowVisible` is `false`). It has no effect on: the 24-hour view (no daily high/low concept exists there), the Rain/Cloud tabs (no high/low concept for those metrics — Rain is a bar total, Cloud is an average-only line per `003-extended-history-metrics` research.md §3), or the details table (`ObservationDetails.tsx`'s daily table already shows high/low/average columns unconditionally and continues to do so, per this spec's Edge Cases).

## 4. Wind high/low daily aggregation (FR-009, FR-010, User Story 4)

**Decision**: Extend `DailyAggregate` with two new fields, `windHigh`/`windLow` (`number | null`), computed in `services/dailyAggregation.ts`'s `toDailyAggregates` exactly the way `high`/`low` are already computed for temperature — `Math.max(...windSpeeds)`/`Math.min(...windSpeeds)` over that bucket's non-null `windSpeed` readings, `null` if the bucket has none (same gap rule as every other aggregate field).

To render them, factor the existing temperature-daily row-building logic in `components/chartData.ts`'s `buildDailyRows` into a shared, metric-parameterized helper — `buildHighLowAverageDailyRows(primary, nearbyStations, unit, bucketCount, fields, convert)`, where `fields` selects `{high, low, average}` off `DailyAggregate` (`{ high: "high", low: "low", average: "average" }` for temperature, `{ high: "windHigh", low: "windLow", average: "windAverage" }` for wind) and `convert` is `convertTemperature`/`convertWindSpeed` respectively. `buildDailyRows` (temperature) becomes a thin wrapper adding the precipitation-bar field on top of this shared helper's output; a new `buildWindDailyRows` wrapper calls it directly (no bar field, since wind has no precipitation-style total). `ObservationChart.tsx`'s wind branch, for the 7-day/30-day windows, switches from today's single `windAverage`-only line (via `buildMetricDailyRows`, `003-extended-history-metrics`) to three lines (high/low/average) built from `buildWindDailyRows`, styled identically to the temperature daily branch (same `HIGH_COLOR`/`LOW_COLOR`/dash pattern, same `highLowVisible` conditional rendering) — this is the literal "re-use the max/min avg setup from temperature" the feature asks for. Wind's 24-hour (hourly) view is unchanged — it still shows a single instantaneous-reading line, exactly like temperature's 24-hour view, since neither has a "high/low" concept at hourly resolution.

**Rationale**: This is the smallest change that satisfies "re-use the setup" literally — one shared row-builder function powering both metrics' three-line daily view, rather than a second, independently-written near-duplicate of `buildDailyRows`. It also keeps `003-extended-history-metrics`'s single-line `buildMetricDailyRows`/`METRIC_FIELDS` machinery intact for Rain and Cloud (which still only ever need one primary value per series) — this feature doesn't touch those two metrics' code paths.

**Alternatives considered**: Generalizing `METRIC_FIELDS`/`buildMetricDailyRows` (from `003-extended-history-metrics`) to optionally carry a `{high, low}` pair too — rejected as it would force Rain/Cloud's simpler single-value contract to carry unused `high`/`low` fields, adding complexity to a code path this feature doesn't need to touch, for no benefit over a separate, explicitly-named helper for the two metrics that actually have a high/low concept.
