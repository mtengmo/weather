# Research: More Granular Weather Icons and a Slimmer Graph Header

## US1a — Low-confidence rain/snow guard

**Finding**: `deriveWeatherCondition()` classifies rain/snow purely from `precipitation > 0` (an amount in mm) — it never looks at `chanceOfRain`, even though every provider already supplies it (`WeatherObservation.chanceOfRain`, aggregated as `DailyAggregate.chanceOfRainMax`) and it's already plumbed into every call site that needs an icon (just not passed to `deriveWeatherCondition` itself). This is the exact, traceable cause of the reported bug: a day with a tiny forecast amount and a 7% chance still shows the rain icon.

**Decision**: Add an optional `chanceOfRain?: number | null` field to `WeatherConditionInput`. In the amount-based branch only (`precipitation !== null && precipitation > 0`), skip returning rain/snow when `chanceOfRain` is present and below a new `LOW_CONFIDENCE_CHANCE_OF_RAIN_PERCENT` threshold (20%) — falling through to the existing windy/cloud/clear checks instead. Threshold picked comfortably above the reported 7% and comfortably below a coin-flip, per spec Assumptions ("in the neighborhood of the 7% the request calls out").

**Scope boundary**: The guard applies only to the plain amount-threshold branch, not to `symbolCondition`-based rain/snow (the `SYMBOL_PRECIPITATION_CONDITIONS` short-circuit above it) — a source's own official symbol code is already that provider's own confident categorical judgment, not a threshold guess this app is making from a raw number. Only `ObservationDetails.tsx`, `timelineData.ts`'s two icon-affecting calls (not its two `isSnowyCondition` calls — see below), `TodaySummaryCard.tsx`, `WeeklyForecastStrip.tsx`, and `WeatherIconOverview.tsx`'s `currentCondition` call are updated to pass `chanceOfRain`/`chanceOfRainMax` through; `isSnowyCondition`'s two call sites (routing a bar to the rain vs. snow row) are left unchanged, since suppressing a bar's row entirely on a low-confidence period would fight the timeline's own existing separate chance-of-rain opacity/display treatment (011-precipitation-chance) rather than complementing it.

**Alternatives considered**: Requiring a minimum precipitation amount instead of using chance-of-rain — rejected because the actual reported bug already has a real (if tiny) amount; the missing signal is confidence, not magnitude. Gating symbol-code-based conditions too — rejected per the scope boundary above.

## US1b — Partly-cloudy vs. cloudy

**Finding**: Every provider this app uses already distinguishes two cloud tiers, and today's code discards the distinction:
- **SMHI** (`smhiProvider.ts`, Wsymb2 table): codes 3-4 ("Variable cloudiness"/"Halfclear sky") and 5-6 ("Cloudy sky"/"Overcast") are *all four* currently folded into one `"cloudy"` entry.
- **MET Norway** (`metNoProvider.ts`): symbol names `fair`/`partlycloudy` and `cloudy` are *all* currently matched by one substring check (`code.includes("cloud") || code.includes("fair")`) into `"cloudy"`.
- **Open-Meteo**: no symbol code, only a raw `cloud_cover` percent — already the fallback path (`cloudCoverPercent >= CLOUDY_THRESHOLD_PERCENT`) once no symbol condition applies.

**Decision**: Add `"partly-cloudy"` to `WeatherCondition`. Split each source: SMHI codes 3-4 → `"partly-cloudy"`, 5-6 → `"cloudy"`; MET Norway `fair`/`partlycloudy` → `"partly-cloudy"`, `cloudy` → `"cloudy"` (checked as an exact/prefix match, not the current loose `includes("cloud")`, to avoid accidentally matching `partlycloudy` before the more specific check). For the generic cloud-cover-percent fallback (Open-Meteo, or any period with no symbol code at all), keep the existing `CLOUDY_THRESHOLD_PERCENT` (50%) as the clear/cloudy boundary unchanged, and add a second, higher boundary `OVERCAST_THRESHOLD_PERCENT` (80%) splitting the former single "cloudy" range into `"partly-cloudy"` (50-79%) and `"cloudy"` (80-100%, now meaning "heavily overcast"). `"partly-cloudy"` joins the existing `symbolCondition === "cloudy" || "clear-day" || "clear-night"` short-circuit list so a symbol-classified value passes straight through as today's `"cloudy"` already does.

**Icon**: `lucide-react` already ships `CloudSun`, a natural "partly cloudy" glyph distinct from the existing `Cloud` (used for `"cloudy"`) — no new dependency. No day/night split for either tier, matching the existing (day/night-agnostic) `"cloudy"` entry's own pattern, for consistency and to avoid a scope increase spec.md didn't ask for.

**Alternatives considered**: A three-or-more-tier cloud scale (e.g. matching SMHI's own 4 raw codes 1:1) — rejected as more granularity than requested ("more granular," not "maximally granular") and it would need an invented mapping for MET Norway/Open-Meteo, which don't naturally support that many tiers.

## US2 — Graph view mobile header

**Finding**: No `position: sticky` or `position: fixed` exists anywhere in the app's own header/graph CSS (checked `index.css` in full) — the reported "sticky" effect is the *combined height* of `.app-header` (which stacks into a full column on a ≤480px viewport) plus `ObservationChart`'s own `.window-toggle` and `.metric-tabs` rows (each a set of buttons with no wrapping control, so they can each break onto two lines at narrow widths) all sitting above the chart in normal document flow — tall enough on a typical phone screen to feel permanently "stuck" even though it does scroll away.

**Decision**: Two changes, both mobile-only (via the existing `@media (max-width: 480px)` breakpoint) so desktop is unaffected (FR-008): (1) show the graph's own (currently screen-reader-only) location title inline, to the left of the window-toggle buttons, in one row — satisfying FR-007 directly and removing a level of implicit vertical redundancy with the app-header above it; (2) make `.window-toggle` and `.metric-tabs` horizontally scrollable single-row strips at that breakpoint (`overflow-x: auto; flex-wrap: nowrap`) instead of letting their buttons wrap onto a second line — the same horizontal-scroll-instead-of-wrap pattern this codebase already uses for the Overview timeline (`.weather-timeline-wrap`), so it's idiomatic rather than a new interaction pattern.

**Accessibility**: The graph's `<h2>` stays in the DOM for the existing focus-on-view-change behavior (`headingRef.current?.focus()`), but drops `visually-hidden` at the mobile breakpoint only were it re-used as the visible inline title — to avoid two competing copies of the same text, the existing hidden `<h2>` is reused as the visible title (styled inline, not duplicated as a second element), satisfying FR-009 (still an equivalent announcement) without adding new markup.

**Alternatives considered**: Collapsing `.app-header` itself further on the graph view specifically — rejected as a shared-header change with a much larger blast radius (affects every view, not just the graph) for a problem this spec scopes to the graph view alone (spec Assumptions: "Overview and its own header/timeline are out of scope").
